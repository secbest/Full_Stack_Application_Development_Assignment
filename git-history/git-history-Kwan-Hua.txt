    feat(leakage): let a leakage row be reviewed, closed and reopened
    
    The revenue-leakage report could only ever accumulate. Prevention
    (surcharges price from a published rate card, so a booking with no
    contract still gets priced) and detection (the report) were both in
    place, but a gap that had genuinely been dealt with had no way to leave
    the total.
    
    That matters most for the case the report cannot fix itself. Once an
    invoice has been pushed to Xero the bill is issued, and EFAR is
    pre-accounting - Xero is the master ledger, so silently re-pricing an
    issued document is exactly what this system must not do. The only honest
    resolutions are "billed the difference separately" or "written off", and
    neither could be recorded. So the figure drifted further from reality
    every month and the report became easy to ignore, which is the worst
    outcome for a report whose only job is to be acted on.
    
    Adds PATCH/DELETE /api/dashboard/revenue-leakage/:invoiceId/dismiss,
    restricted to the AR Specialist and the MD - the wider read access on
    the report deliberately does not extend to writing off revenue.
    
    Design decisions worth stating:
    
    - The reason is mandatory, min 10 chars. A blank or one-word note
      ("ok", "n/a") records that a decision happened without recording why,
      which is the same as not recording it.
    - An actor column is stored alongside the timestamp and reason. A
      write-off with no attributable author is not an audit trail, and this
      is the one action in the report that decides money will not be
      collected.
    - Dismissing does NOT clear unpriced_surcharges. That column is the
      evidence behind the decision; erasing it would make the dismissal
      unauditable and the figure unreproducible.
    - Closed rows are reported separately with their own total, never merged
      into the open figure and never hidden. Folding them in would let a
      write-off look like a fix; dropping them would erase the decision.
    - Dismissal is reversible. A write-off that cannot be undone is one
      nobody dares make, and the feature would go unused.
    - Re-dismissing an already-closed row is refused rather than silently
      overwriting the first reason and author.
    
    Stored on invoices, not bookings. Booking already carries an unused
    leakage_dismissed_at/reason pair, added speculatively and read by
    nothing - but leakage is an invoice-level fact (unpriced_surcharges
    lives on invoices, and the report is keyed by invoice_id), so the
    dismissal belongs beside the data it closes out. The dead Booking
    columns are left alone; removing them is a separate cleanup.
    
    Migration is idempotent and re-reads information_schema to confirm each
    ALTER actually took effect, and is wired into db:setup and db:reset.
    There is no backfill: every existing row is undismissed, which is what
    NULL already means - writing a value would invent a decision nobody made.
    
    Also fixes todayISO() on the report page, which had the same
    toISOString() day-shift as the backend helper and would have sent
    yesterday as the range end before 08:00 Singapore time.
    
    Backend 47 suites / 503 tests, frontend 38 suites / 308 tests, build clean.

    fix(dashboard): anchor MD date ranges to the local calendar day
    
    Every figure on Doris's Executive Dashboard read one day behind. Even an
    explicit date_from=2026-08-08&date_to=2026-08-08 came back as 2026-08-07,
    so "Today" showed yesterday's bookings and no filter could reach today.
    
    toDateOnly() formatted via .toISOString(), which converts to UTC first.
    Every Date reaching it is anchored to LOCAL midnight, from one of two
    places:
    
      - resolvePeriodRange() builds it with startOfDay(new Date()).
      - Yup.date() in fleetOverviewQuerySchema/vendorExpensesQuerySchema
        coerces a bare "2026-08-08" param to local midnight. Yup parses
        date-only strings as local; native new Date() parses them as UTC,
        which is why the two behave differently and this is easy to miss.
    
    In Singapore (UTC+8) local midnight is 16:00 the previous day in UTC, so
    slicing the ISO string moved the calendar day back by one. Reading the
    local date components instead keeps it intact.
    
    One function, so all 12 call sites are corrected: fleet-overview (both
    ends, including caller-supplied dates), vendor-expenses' default end of
    range, and revenue-trend's week bucket labels. The five sibling schemas
    already validated dates as YYYY-MM-DD strings and were never affected -
    this is the same Singapore-timezone class of bug fixed for TIMESTAMP
    columns in c9ecc49, on the path that fix did not cover.
    
    Visible effect: the Reports page disagreed with itself. Its Revenue,
    Billing Cycle and Leakage History tabs were correct while Vendor
    Expenditure on the same screen was a day behind.
    
    Tests pin literal expected dates rather than recomputing them the way
