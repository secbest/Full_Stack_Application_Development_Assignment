## Key Decisions Made

- **Delete is deliberately narrow, not a general-purpose row delete.** Intake: only `rejected` submissions (pending is still awaiting a decision; confirmed already produced a `Booking` via `intake_submission_id`, so deleting it would orphan that booking or hit an FK violation). Bookings: only `invoiced` (by that stage Xero holds the master copy, so the local record is safe to clear as completed clutter).
- **Cascade the delete, but keep `XeroSyncLog`.** Deleting an invoiced booking also deletes its `ServiceMemo`, `Invoice`, `InvoiceLineItem`s, and `JobMilestone`s in one transaction - but *not* its `XeroSyncLog` rows. This was an explicit discussion with Bao: the sync log is the only thing left standing as evidence a sync happened, once the rest of the operational record is gone.
- **`ConfirmDialog` over `window.confirm()`.** Bao wants destructive-action confirmations styled like the rest of the app, not a native browser popup - `ConfirmDialog.jsx` is now the shared component for this, currently used by both delete flows. (Note: `ContractDetailPage.jsx`/`ContractFormPage.jsx` elsewhere in the app still use `window.confirm()` - not touched this session, so the two patterns currently coexist.)
- **Whole row is clickable, not just the button.** After the hover-removal bug report, settled on: the `<tr>` opens the review/detail modal on click, and the explicit "Review"/"Delete" buttons stay (for discoverability + the icon/label affordance) but `stopPropagation()` so they don't double-fire the row's handler.
- **No forced scrollbar in the current state.** Went back and forth on `overflow-y-auto` vs `overflow-y-scroll` vs a fixed `max-h` with a sticky header, then Bao asked to revert it. Landed (for now) on no vertical scroll constraint at all on either table - flagged below as something to revisit deliberately rather than by accretion.
