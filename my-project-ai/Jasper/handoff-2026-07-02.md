## Session 1 - Planning and Domain Clarification

### What We Worked On

This was a planning and domain clarification session - no code was written. The focus was on understanding the EFAR workflow and aligning on implementation approach before coding begins.

### Key Questions Answered

#### 1. Post-Intake Workflow (AR Flow)
Clarified the full end-to-end flow after a customer submits the public intake form:

1. Customer submits intake form (public route, no auth) - creates `intake_submissions` record
2. Camilla (Quotations Specialist) reviews in Intake Queue - confirms or rejects
3. On confirm - booking created, Ravi (Field Crew) sees job in My Jobs
4. Ravi completes job and submits 4-step Memo Wizard - creates `service_memo`
5. Sarah (AR Specialist) reviews memo in Memo Review Queue - approves or returns
6. On approve - pricing engine auto-matches against `pricing_contracts` table, draft invoice generated
7. Sarah approves invoice and syncs to Xero as a draft

#### 2. Booking Status Meanings
The statuses "Confirmed / In Progress / Completed (Memo Pending) / Invoiced" are **booking lifecycle statuses** (visible in Booking List and Executive Dashboard Fleet tab), NOT AP-specific statuses:

| Status | Meaning |
|---|---|
| Confirmed | Intake approved by Camilla, booking record created |
| In Progress | Ravi is currently on the job |
| Completed (Memo Pending) | Job done but Service Memo not yet submitted - revenue leakage risk, shown as red rows |
| Invoiced | Full AR flow complete - memo approved, priced, invoice synced to Xero |

The AP Dashboard's own stat cards are separate: **Pending / Low Confidence / Synced / Failed** (vendor invoice OCR states).

#### 3. Notifications in AP Account
The bell icon / notifications panel in the AP account is a **placeholder UI element** with no backend function. Not scoped in the project spec. The app handles alerts via:
- Toast notifications (bottom-right, 3s auto-dismiss, green/red)
- Dashboard stat cards as the "needs attention" summary

No notifications table exists in the schema. The icon can be removed or left as a known placeholder.

#### 4. Table Implementation Decision
**Decision: shadcn/ui DataTable (built on TanStack Table v8)**

Rationale:
- Already in the tech stack (shadcn/ui specified in CLAUDE.md)
- Handles sorting, filtering, pagination, row selection out of the box
- Fully composable - custom cells, status badges, row coloring are straightforward
- Consistent with existing design tokens

Screens that need tables and their specific requirements:

| Screen | Key requirements |
|---|---|
| Intake Queue | Time-in-queue coloring (amber >2h, red >4h), [Review] action column |
| Booking List | Risk rows (#FEF2F2) for missing memos, memo status column |
| Memo Review Queue | Overdue rows in red |
| Invoice List | 6 status types, batch approve button |
| Vendor Invoice List | OCR confidence % with color coding |
| Pricing Contracts | Expired rows at 50% opacity |

**Rejected alternatives:** AG Grid / MUI DataGrid (overkill, breaks design token consistency), plain `<table>` (no sorting/pagination).

- **Opaque validation error on submit**: the overtime-consistency rule (UC-03: jobs over 8 hours need overtime hours logged or a note) was only enforced backend-side, so it silently passed 3 wizard steps and failed with a generic message at the very end. - **Review card spacing**: `Step4StampSubmit.jsx`'s review rows used `justify-between` with no gap, so long wrapped values (like the destination address) crowded the label. Added `gap-4`/`shrink-0`/`text-right`.
