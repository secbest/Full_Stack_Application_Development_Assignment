### Key Decisions Made

- **`job_milestones` as a separate child table, not columns on `bookings`.**
  Reasons: `bookings` is Zheng Bao's model and already carries a cross-team note
  about temporary field-ops routes; a child table records *who* tapped and *when*,
  is naturally idempotent (unique constraint per booking+type), and needs no
  `bookings` migration. `recorded_at` is always server-set - the tap itself is the
  event, so backdating isn't possible even by an honest mistake.
- **Recording `activated` is the new "start job" trigger.** Previously a `confirmed`
  booking only became `in_progress` as a side effect of crew assignment (see
  `Booking.js`'s status comment) - there was no real "Start Job" action. Now
  recording the first milestone does this, finally giving the My Jobs "Start Job"
  button (previously permanently disabled) a working action.
- **Current-job hero selection**: earliest `in_progress` job wins; failing that, the
  earliest `confirmed` job scheduled today whose start time is within the next hour
  (matching EFAR's stated ~1-hour call-centre lead time). Completed/invoiced jobs are
  never eligible.
- **Milestone stepper is a breadcrumb, not a list** - deliberately reusing an
  *existing* pattern (`WizardProgressBar`) rather than inventing a second stepper
  style, after the original vertical-list version was flagged as too tall. Tradeoff
  named to the user: only one timestamp is visible at a time (the caption line);
  earlier ones are one tap away on their own circle, not lost.
- **"Upcoming jobs" = has something left to do, not "every booking ever."** A
  completed/invoiced booking's memo is already submitted - that belongs in Memo
  History, not a second, misleadingly-labeled list on My Jobs. This was a genuine
  bug (no status filter existed), not just a UX preference.
- **Declined to auto-fill `job_start_time` from the booking's scheduled time**, even
  though it would reduce typing when no milestone was recorded. The scheduled time
  is the *planned* time set before the job happened, not the real activation time -
  falling back to it would let a wrong value look legitimate and silently
  reintroduce the inaccurate-billing problem item 1 exists to close. No code change
  from this - purely a recommendation the user accepted.
- **`try/catch` audit is a systemic gap, not a one-off fix.** `listMyJobs`/
  `getBookingById` were fixed because they were live-fired this session, but
  `listBookings`/`updateBookingCrew` in the same file already had the pattern -
  meaning other controllers may have the same gap. Flagged as worth a project-wide
  check, not assumed fixed everywhere.
- **Root-caused both flaky-test fixes rather than silencing them** - the
  `ContractDetailPage` fix targets the actual accessible-name mismatch;
  the `ContractFormPage` fix targets the actual per-test time cost (measured
  before/after: ~3-4s -> 371-761ms), not just a bumped timeout.
- **Deployment is explicitly deferred until all functions across the team are
  complete** - the user stated this mid-session; noted in memory so it isn't
  re-litigated or assumed otherwise in a future session.
- **PR merged via GitHub's web UI, not `gh` CLI** - `gh` isn't installed on this
  machine. Rather than search for credentials/tokens to script around that, gave
  the user a pre-filled compare URL and description to complete manually. Worth
  installing `gh` (`winget install --id GitHub.cli`) if this comes up again.

## Session 3 - NotificationBell "Mark All As Read" Bug Fixes

### What We Worked On

The user reported that clicking "Mark all as read" in the notification bell
(built in Session 2, above) didn't clear the notifications. This turned out to be
**two separate, unrelated issues** surfaced by the same user action - a real race
condition, found first, and then a UX expectation mismatch, found only after asking
for a screenshot.

1. **Used `systematic-debugging` rather than guessing at a fix.** Read
   `NotificationBell.jsx`, `notificationController.js`, and the design spec first;
   all three looked correct on inspection, and the existing mocked Jest tests
   (backend 8/8, frontend 8/8) already passed - a mocked-test pass that would have
   hidden this bug either way, since the bug is a real-network-timing race no unit
   mock naturally exercises.
2. **Reproduced live against the real dev DB and running app before touching any
   code.** Seeded 3 real unread `Notification` rows for `camilla@efar.com.sg` via a
   throwaway script, then drove the actual app (both dev servers were already
   running) with a headless Playwright script: logged in, opened the bell, clicked
   "Mark all as read", and inspected the actual network responses. The full round
   trip worked - `PATCH /api/notifications/read-all` returned success and a
   follow-up `GET /api/notifications` confirmed `is_read: true` persisted in the
   real database. **Could not reproduce a bug this way**, which mattered: it ruled
   out "the endpoint doesn't work" before guessing further.
3. **Asked the user a clarifying question** (`AskUserQuestion`) rather than guessing
   which of several plausible symptoms they meant, since Phase 1 (reproduce)
   couldn't be completed from investigation alone. The user picked "it clears, then
   [the badge] comes back" - which pointed at a timing race, not a broken endpoint.
4. **Root-caused the race**: `refreshUnreadCount()` (called on mount, every 30s
   poll, and on `visibilitychange`) had no protection against an in-flight request
   resolving out of order. If a poll's `GET /unread-count` was already in flight
   when the user clicked "Mark all as read," the click's optimistic
   `setUnreadCount(0)` would run, then the older poll's response would land
   afterward carrying the stale pre-click count and silently overwrite it back.
5. **Wrote a failing test first** reproducing the exact race (a controlled,
   manually-resolved pending promise standing in for the stale poll response). The
   first version of the test passed against the *unfixed* code - a false negative
   caused by `jest.advanceTimersByTimeAsync(0)` not flushing enough of React's
   scheduler under fake timers. Diagnosed that directly (temporarily asserting the
   opposite outcome to confirm the stale response really was reaching state) before
   trusting the test, then fixed the test itself (switch to real timers after
   triggering the stale resolution) to get a genuine red before implementing
   anything.
6. **Fixed with a request-sequencing token** (`unreadCountTokenRef`): every
   `refreshUnreadCount()` call captures the current token before awaiting; every
   optimistic write (`handleItemClick`, `handleMarkAllRead`) bumps it first. A
   response is only applied if the token still matches when it resolves - discarding
   any response older than the most recent optimistic update, regardless of network
   arrival order.
7. **User then clarified the actual complaint was different** - a screenshot showed
   4 notifications sitting in the dropdown with no blue unread dots (i.e. correctly
   marked read), but the user expected them to be gone entirely, not merely
   de-highlighted. This is a real design-doc behavior
   (`docs/superpowers/specs/2026-08-05-live-handoff-notifications-design.md`
   describes the dropdown listing "recent notifications," not filtering to unread),
   so this was flagged as a UX decision, not a bug, and put to the user via a second
   `AskUserQuestion` rather than silently changed.
8. **Implemented "dropdown shows unread only"** per the user's choice: the list
   fetch now requests `unread_only=true` (an endpoint capability that already
   existed from Session 2, just unused by the frontend); a single item disappears
   from the local list the instant it's clicked (instead of staying with its dot
   removed); "Mark all as read" now clears the list to empty immediately, showing
   the existing "No notifications yet." empty state.
9. **TDD'd both behavior changes**: 2 new tests (dropdown fetch includes
   `unread_only: 'true'`; "Mark all as read" empties the list and shows the empty
   state), confirmed failing against the pre-change code, then passing after.
10. **Verified with the full frontend suite twice** (once per fix): 162/162, then
    163/163 (net: 3 new tests added across the two fixes, one existing test
    renamed/extended rather than duplicated). No backend changes were needed - both
    issues were entirely frontend-side.
11. **Cleaned up every debug artifact from the real dev database and disk** before
    finishing: the 3 seeded debug notifications for `camilla@efar.com.sg` were
    deleted via the same throwaway script (which was itself deleted, never
    committed), and the scratch Playwright repro script was left only in the
    session scratchpad, not the repo.

### Key Decisions Made

- **Investigated before touching code, even though the fix ended up small.** The
  `systematic-debugging` skill's Phase 1 (reproduce) genuinely failed on first
  attempt - the live round trip worked - which is exactly the situation that
  prevents a wrong guess (e.g. "the PATCH must be silently failing") from being
  shipped as a fix for a bug that wasn't actually there.
- **Asked rather than assumed when reproduction failed.** Two different
  `AskUserQuestion` calls in this session both changed the diagnosis: the first
  ("it clears, then comes back") pointed at a timing race instead of a broken
  endpoint; the second (screenshot + question) revealed a second, unrelated issue
  that investigation alone would never have surfaced, since the "bug" was actually
  the app behaving exactly as the existing design doc specified.
- **Did not trust a test that passed for the wrong reason.** The first version of
  the race-condition test passed against unfixed code - instead of accepting a
  green result, temporarily inverted the assertion to confirm the stale response
  really was reaching component state, found it was, and only then treated the
  original (correctly red) test as valid.
- **Fixed with a generic request-sequencing token, not a special case for
  "Mark all as read."** The same token guards `handleItemClick`'s optimistic
  decrement too, so the identical race (an in-flight poll clobbering a single-item
  read) is closed as well, not just the one path the user happened to notice.
- **Treated "notifications should disappear when read" as a UX decision requiring
  sign-off, not an obvious bug fix** - the existing design spec explicitly
  documented the opposite behavior, so changing it silently would have contradicted
  a decision already recorded as intentional.
- **Did not restart or otherwise touch the dev servers.** Both were already running
  at session start (started by the user or a prior session) and had stopped by the
  time of the second fix's verification pass; per standing project guidance (always
  free ports *you* open), a live re-verification of the second fix was skipped
  rather than starting a new server this session didn't own, and that gap is called
  out explicitly below instead of silently claiming full verification.
