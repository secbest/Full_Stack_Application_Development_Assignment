## Session 4 - Fixed a Singapore-Timezone Bug Making "Today" Silently Drop Early-Morning Records (on `fix/hotfix-bugs-Jasper`)

### What We Worked On

User reported that "Today" wasn't updating on the Dashboard and Reports pages. Traced this to a real, previously-unnoticed timezone bug rather than a UI/refresh problem.

1. **Reproduced live rather than guessing from code alone.** The user's first description ("Numbers don't change when I click Today") matched neither Fleet Overview's Today/This Week/This Month tabs nor Reports' Today/This Month/This Year/Custom period buttons on a code read - both looked like they should refetch correctly on period change. Started both dev servers (both had stopped between messages since the last session) and drove the app with Playwright, logged in as Doris (MD), and confirmed: switching periods on both screens *did* correctly trigger new fetches with different results - so the bug wasn't stale state or a broken click handler.
2. **Found the actual defect by comparing invoice timestamps against the query window.** Fetched the raw invoice list via the API and noticed invoices with `created_at` like `2026-08-07T17:24:39.579Z` - which is 2026-08-08, 01:24am **Singapore time** (UTC+8), i.e. genuinely "today" from the business's perspective, but stored as "Aug 7" in UTC. Compared this against how `ReportPage.jsx` and `dashboardController.js` built their "today" query boundary: both took the LOCAL (Singapore) calendar-date string (e.g. `"2026-08-08"`) and appended a hardcoded `T00:00:00.000Z`/`T23:59:59.999Z` - which reads as **8am Singapore time**, not midnight. Net effect: any record created between local midnight and 8am was silently excluded from "Today," and the window was shifted 8 hours later than the real Singapore day. This is the mechanism behind the report: checking the dashboard in the early morning (or any time, really, for that specific 8-hour band) made recently-created data look missing under "Today."
3. **Fixed it in both places the bug independently existed:**
   - Backend (`dashboardController.js`): added `sgDayStart`/`sgDayEnd` helpers that anchor a bare `YYYY-MM-DD` string to Singapore local time (`+08:00`) instead of UTC, and applied them to the 4 endpoints that compare a date-only boundary against a TIMESTAMP column - `revenueLeakage`, `cycleTime`, `revenueByServiceType`, `leakageHistory`. (`vendorExpenses` and `fleetOverview` were untouched - they filter DATE-only columns, `invoice_date`/`scheduled_date`, which have no time component to shift.)
   - Frontend (`ReportPage.jsx`): the invoice-list fetch had the identical bug independently - it reconstructed a local Y-M-D string and appended a hardcoded `Z`. Replaced with `dateRange.startDate.toISOString()`/`.endDate.toISOString()`, which correctly converts the already-local `Date` objects to their true UTC instant.
4. **Verified the fix live, then with both test suites.** Re-ran the same Playwright reproduction against the restarted backend: Reports' "Today" tab went from `$0.00 / 0 invoices` to `$65.40 / 3 invoices` (the early-morning invoices that were previously excluded), while Fleet Overview's Today/This Week/This Month (unaffected, DATE-only columns) still worked as before. Ran the full backend (43/43 suites, 468 tests) and frontend (32/32 suites, 223 tests) Jest suites - all green, confirming the fix didn't regress anything relying on the old (wrong) behavior.
5. **Started, then cleanly stopped, both dev servers used for verification** - asked the user whether to leave them running for a manual look or stop them; user chose to stop, so both were killed by PID once testing was done, per this project's standing port-cleanup rule.

### Key Decisions Made

- **Reproduce before diagnosing, especially when the code reads as correct.** The user's first-pass description didn't match what the code appeared to do on inspection (both period controls looked like they should refetch fine) - rather than guessing at a second theory from code alone, actually running the app end-to-end (Playwright + real login) surfaced the true mechanism: the numbers *do* update, they're just wrong for "Today" specifically, in a way invisible unless you compare a raw timestamp against the actual query boundary being sent.
- **Fixed at the point where a calendar-date string meets a TIMESTAMP column, not by changing what "today" means everywhere.** `resolvePeriodRange` (used for Fleet Overview's `period=today/this_week/this_month`) already computes correctly, because it builds boundaries from real local `Date` objects on a machine whose OS timezone happens to already be `Asia/Singapore` - left alone. The bug only existed in the 4 endpoints (plus the Reports invoice fetch) that took an already-stringified `YYYY-MM-DD` and re-parsed it assuming UTC.
- **Used a fixed `+08:00` offset, not a timezone library.** Singapore Standard Time has no DST and the business only operates there (per `CLAUDE.md`), so a hardcoded offset is correct and simpler than pulling in a timezone-conversion dependency for one fixed, permanent offset.
- **Left `vendorExpenses`/`fleetOverview` untouched deliberately**, rather than applying the same helper everywhere for consistency - their date columns (`invoice_date`, `scheduled_date`) are DATE-only in Postgres, so a bare `YYYY-MM-DD` comparison against them has no time-of-day component to get wrong in the first place. Changing code that isn't broken would just be noise.
- **Ran both full Jest suites before considering this done**, not just a targeted subset - a timezone-boundary change is exactly the kind of edit whose blast radius isn't obvious from the diff alone (any test seeded with a specific "recent" timestamp could have silently depended on the old, wrong boundary).

### Files Changed

- `backend/src/controllers/dashboardController.js` - added `SGT_OFFSET`/`sgDayStart()`/`sgDayEnd()` helpers; applied them in place of the old `new Date(from)` / `new Date(`${to}T23:59:59.999Z`)` pattern in `revenueLeakage`, `cycleTime`, `revenueByServiceType`, and `leakageHistory`.
- `frontend/src/pages/dashboard/ReportPage.jsx` - the invoices-fetch effect now sends `dateRange.startDate.toISOString()`/`dateRange.endDate.toISOString()` instead of reconstructing an ISO string from `toYMD()` + a hardcoded `Z` suffix.

**Verification:** live Playwright reproduction (login as MD, compare raw invoice `created_at` values against the "Today" query window) before AND after the fix, confirming the exact before/after numbers ($0.00/0 invoices -> $65.40/3 invoices) on the Reports page; full backend Jest suite (43/43 suites, 468 tests) and full frontend Jest suite (32/32 suites, 223 tests), both green after the fix.

### What Still Needs to Be Done

- [ ] **Not committed/merged as of this handoff being written** - check the git log immediately after this entry for whether the commit-then-merge-to-main this session ended with actually landed cleanly.
- [ ] **No automated regression test added for this specific bug** (an invoice/milestone timestamped just after local midnight but before 8am should count under "Today"). Everything here was verified live and via the existing suites (which happened to still pass, but weren't testing this exact boundary before or after) - worth adding a dedicated test asserting the Singapore-local day boundary, so this can't silently regress if someone touches these date helpers later.

If EFAR is ever deployed to a server running a different system timezone (common for cloud VMs, which often default to UTC), `resolvePeriodRange`'s Fleet Overview path (untouched this session, since it works correctly here) would need the same `+08:00`-anchoring treatment this session applied elsewhere - it currently only works "by accident" because this machine's own clock is already Singapore time.

## Session 5 - First Production Deploy to Vercel/Render: Pre-Deploy Audit, Then Three Live Bugs Fixed in Sequence

### What We Worked On

The app's first deployment to Vercel (frontend) + Render (backend) + Supabase (shared DB, same instance as local dev), done live over several rounds as each fix surfaced the next problem.

1. **Pre-deployment audit** (before anything was live) - reviewed the codebase against `design/architecture.md` for hardcoded URLs/credentials, CORS config, Sequelize's `DATABASE_URL` usage, Cloudinary config, and route error-handling coverage. Found everything already correctly env-driven and try/catch-covered; flagged (but didn't yet fix) several deploy-config gaps: no `vercel.json` SPA rewrite, an unused `VITE_GEMINI_API_KEY`, and `deployment.md` being stale (local-dev-only, missing the Vercel/Render/Supabase production picture).
2. **Rewrote `deployment.md`** per the user's spec - a Cloud Services table with public-URL placeholders (Frontend/Backend/Database/Image Storage), then full env var tables grouped by service, descriptions only, no real values.
3. **Fixed the health-check startup log** (`backend/src/index.js`) - it always printed `http://localhost:${PORT}/health` even in production. Now uses Render's auto-populated `RENDER_EXTERNAL_URL` when present. Cosmetic (the `/health` route itself always worked), but confusing in Render's logs.
4. **Bug 1 live: refreshing any non-root route 404'd on Vercel.** Root cause: no `vercel.json` rewrite, so Vercel's static host looked for a literal file/path instead of falling through to `index.html` for React Router to handle. Added `frontend/vercel.json` with a catch-all rewrite to `/index.html`.
5. **Bug 2 live: login showed `"Route POST /auth/login not found"`.** Root cause: `VITE_API_BASE_URL` was set on Vercel to the bare Render URL without the `/api` suffix, but every frontend API call is a relative path (`/auth/login`) that assumes the base already ends in `/api` (`frontend/src/api/index.js`). Fixed by setting `VITE_API_BASE_URL=https://full-stack-application-development.onrender.com/api` on Vercel.
6. **Bug 3 live: login showed `"Invalid email or password."` with correct credentials.** Diagnosed by testing the backend directly with `curl` first (confirmed the DB, password hash, and JWT signing were all correct - the demo account logged in fine over HTTP) rather than assuming the DB was the problem. Then reproduced the actual browser request with `curl -H "Origin: <vercel-preview-url>"` and found the mismatch: the user was testing on a Vercel **preview** URL (`...-git-7f2c43-secbest-hq.vercel.app`), but `FRONTEND_URL` on Render was pinned to the single production alias (`...-pi.vercel.app`). `cors()` with a static string origin always echoes that one configured value regardless of the request's real origin, so the browser's CORS check failed, the request never resolved to a response, and `LoginPage.jsx`'s catch-all fallback (`err.response?.data?.message || 'Invalid email or password.'`) displayed a misleading credentials-error message for what was actually a CORS rejection. Fixed by changing `backend/src/index.js`'s CORS `origin` from a fixed string to a function that accepts both the exact `FRONTEND_URL` and any origin matching `/^https:\/\/full-stack-application-development[a-z0-9-]*\.vercel\.app$/`, so every Vercel preview deployment works without updating `FRONTEND_URL` per-branch.
7. **Also fixed a related code smell found while investigating Bug 3**: `authController.js`'s `login` catch block returned `"Invalid email or password."` (401) for *any* unexpected error, including genuine server-side failures (DB connection errors, etc.) - meaning a real 500 would have been indistinguishable from a bad password with no server-side log to tell them apart. Changed it to log the real error (`console.error('[auth] login failed unexpectedly:', err)`) and return a proper 500/`INTERNAL_ERROR` for anything that isn't a validation error, so this can't happen silently again.
8. **Restricted the Live Fleet Tracker map to Singapore** (`frontend/src/components/FleetMap.jsx`) - added a `restriction` bounding box (covering the main island plus outlying islands like Sentosa/Pulau Ubin) with `strictBounds: true`, plus a `minZoom: 11` floor, so the map can't be panned or zoomed out past Singapore. Verified with `npm run build` before pushing since this was requested "safely" during active deployment.
9. **Updated `CLAUDE.md`** with a new "Deployment (Vercel + Render + Supabase)" section documenting the live URLs, the required deploy-time config (the `/api` suffix, the CORS regex, `NODE_ENV=production`, `vercel.json`, `XERO_SIMULATION`), and the three gotchas above so they're recognized immediately if they resurface (e.g. after a Vercel project rename, or a teammate's fresh deploy).
10. Every fix in this session was committed and pushed to `main` individually as it was diagnosed and resolved, matching the user's request to "push this main" / "commit and push to main safely" - see Files Changed below for the four resulting commits.

### Key Decisions Made

- **Test the backend directly with `curl` before assuming the database or credentials are wrong.** When "Invalid email or password" appeared despite correct-looking credentials, curling the live Render URL directly (bypassing the browser entirely) proved in one request that the DB/password/JWT path was fine - which immediately ruled out an entire category of possible causes and pointed straight at the network/CORS layer instead.
