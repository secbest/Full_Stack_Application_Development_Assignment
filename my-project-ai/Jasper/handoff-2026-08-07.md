### What Was Built

A new Managing-Director-only **Fleet Tracker** page (`/fleet-tracker`) showing every field crew member's live status and position on a Google Map, addressing the gap that Doris had no way to see where crews actually were without asking around.

1. **Backend: `GET /api/dashboard/crew-positions`** (`managing_director`-only) in `dashboardController.js`, added in `991fd79`:
   - For every `field_crew` user, derives a `status` of `available` | `en_route` | `on_scene` | `off_duty`:
     - No active (`in_progress`) booking → `available` if `last_active_at` is within the same 5-minute "Currently Online" window Accounts Management already uses, else `off_duty`.
     - Has an active booking → status and position both derived from that booking's latest `JobMilestone` in sequence: `activated` (or nothing yet) → `en_route` heading to pickup; `arrived_at_location` → `on_scene` at pickup; `en_route` (milestone) → `en_route` at the midpoint between pickup and destination (jittered ~200m so overlapping crews don't stack exactly); `arrived_at_destination`/`job_completed` → `on_scene` at destination.

The fleet tracker polls every 30s, and most addresses repeat across polls/crew, so this avoids re-hitting the Geocoding API (and burning quota) for the same address twice. Handles the race where two concurrent polls both miss the cache and try to insert the same address (`SequelizeUniqueConstraintError` is treated as success, not a real failure).

### Key Decisions (inferred from the code)

- **Positions are derived from real milestone events, not simulated on a timer.** A crew member's pin only moves when an actual `JobMilestone` (tapped by the crew in "My Jobs") says it should - avoids the map showing fake "live" movement disconnected from what's actually happening in the field.
- **Geocoding is cached in Postgres, not called fresh on every poll.** A naive implementation re-geocoding every crew's pickup/destination/HQ address every 30 seconds would burn Google Geocoding API quota fast across multiple concurrently-open MD sessions; the cache keys on exact address text and is shared across all crew/all pollers.
- **Idle crew share a deterministic, not random, position spread around HQ.** Random jitter on every poll would make stationary crew appear to "wander" near HQ on the map for no reason; the golden-angle offset is a pure function of crew id, so it's stable across polls and only genuinely moving crew (the `en_route` jitter) look like they're actually moving.
- **A minimap-first, expand-on-demand layout**, not a full-page map by default - keeps the map from dominating the Fleet Tracker page unless Doris actually wants to zoom in and read positions closely.
- **Labels and the roster panel were added reactively, in a follow-up commit**, once the initial ship revealed pins were anonymous until clicked - a real usability gap caught after the first version, not designed in from the start.

## Session 3 - Login Case-Sensitivity, Field Crew Job Rejection, Crew Availability, and Small UX Fixes (on `feature/field-crew-roles`)

### What We Worked On

Started from a login bug report and worked through a series of small, mostly-independent fixes and one real feature addition (field crew job rejection), all on `feature/field-crew-roles` rather than `main`.

1. **Fixed case-sensitive login.** User could log in with `ravi@efar.com.sg` but not `Ravi@efar.com.sg` - Postgres string equality is case-sensitive by default, so `User.findOne({ where: { email } })` treated them as different rows. Added a Sequelize setter on `User.email` that lowercases/trims on every write, and lowercased the lookup value everywhere the app queries by email (login, register, and both "email already in use" checks in `userController`). No migration needed since existing seed data was already lowercase.
2. **Made the login page's EKG/heartbeat trace animate continuously.** It previously drew once on page load and then sat static. First pass added a draw-hold-fade-redraw loop; user disliked the fade, so it was replaced with a continuous linear sweep (dash length = gap length = path length, `stroke-dashoffset` animating to `-300` on an infinite loop) - draws in and recedes forever with no fade, no flash.
3. **Added field-crew availability status to the crew-assignment picker** (Booking Detail's "Crew Assignment" dropdown, `BookingListPage.jsx`) after discussing with the user that assigning a job to a crew member already out on another job was a real scheduling gap. `GET /api/users?role=field_crew` now also returns `on_job` (has an `in_progress` booking) and `active_job_count` (confirmed + in_progress bookings), computed from the `Booking` table in `userController.listUsers`. The picker shows a colored pill per crew member: amber "On Job", blue "N Scheduled", or green "Available".
4. **Fixed the Quotations "Review Submission" modal being too tall to complete without scrolling.** Restructured the modal into a fixed-height flex layout: header stays fixed, the left detail column scrolls independently, and the right Action panel now has its own scrollable field area plus a sticky footer (Confirm Booking / Reject Submission buttons pinned below a border, always visible without scrolling the whole form).
5. **Deleted a stale confirmed booking** (`BKG-2026-00006`, Nanyang Poly, scheduled 2026-08-05, i.e. already in the past) at the user's request - confirmed via a one-off script that it had no linked memo/invoice/milestones before permanently removing the row from Supabase.
6. **Built field crew job rejection** - the session's main feature. A field crew member can now reject a job (current/in-progress or upcoming/confirmed) from "My Jobs", giving a required reason; the job is unassigned and returned to Quotations rather than staying stuck on a crew member who can't do it.
   - Backend: new `POST /api/bookings/:id/reject` (field_crew or MD only, same "booking not found or not yours" blurred-404 pattern as the existing milestone route). ### Key Decisions Made

- **Normalize email case at the model layer, not just at the login endpoint.** A Sequelize `set()` on the `email` field means every write path (register, admin edits, self-service profile edits) is automatically consistent, rather than patching each call site's write and hoping nothing else writes an un-lowercased email later.
- **Continuous animation over one-shot, and no fade.** First implementation (draw → hold → fade out → redraw) was explicitly rejected by the user for the fade; replaced with a fade-free looping sweep instead of trying to tune the fade timing.
- **Job rejection resets the booking to a clean `confirmed` state, not a new "rejected" status.** There's no `rejected` value in the `Booking.status` enum, and adding one would ripple through every status-driven UI (badges, filters, dashboards). Reusing `confirmed` + `assigned_crew_id: null` means the booking reappears in exactly the queue (Booking List's "unassigned" filter) that already exists for this purpose, with zero new UI needed on the Quotations side.
- **Wipe milestones on rejection rather than preserving them.** If a job was `in_progress` (crew had tapped "Start Job" or further) and gets rejected, the next crew assigned would otherwise inherit someone else's half-recorded timeline, which would corrupt the "current job" hero-selection logic (`selectCurrentJob` in `MyJobsPage.jsx`) and the memo wizard's pre-fill. A full reset back to "not started" was judged less confusing than trying to reconcile old milestones with a new crew.
- **Booking `BKG-2026-00006` was deleted outright, not rescheduled**, per the user's explicit choice when asked - it had zero linked records, so nothing was at risk of dangling.
- **Every destructive or hard-to-verify backend action (deleting a real DB row, adding a route, changing a query) was confirmed live against Supabase before considering the task done** - e.g. running a lookup script before deleting a booking, and a full create-reject-inspect-cleanup cycle for the job-rejection feature and its two follow-on bugs, rather than trusting the code review alone.
