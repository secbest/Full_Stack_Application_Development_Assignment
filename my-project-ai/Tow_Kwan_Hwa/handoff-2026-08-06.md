## What Was Completed

### 1. AR memo approval and unmatched-invoice recovery

- Memo approval now treats "no active contract" and "no matching rate" as a completed review with
  an actionable `unmatched` invoice, instead of committing the invoice and then returning a
  misleading HTTP error.
- Active-contract lookup consistently uses the booking's service date.
- Added `POST /api/invoices/:id/rematch`. After a contract or rate is corrected, AR can select
  **Retry Match** from Invoice Detail to run the pricing engine again.
- An unmatched invoice can alternatively be priced through manual adjustment lines. Adding a
  manual line moves it to `adjusted`, making it eligible for approval.
- Unpriced memo charges are retained and shown explicitly. They are never silently included in the
  invoice total.
- Memo return is blocked once any invoice exists, with guidance to correct the invoice rather than
  leaving the memo and invoice in contradictory states.
- Engine lines that are edited manually are identified separately from genuine manual adjustment
  lines.

### 2. Dynamic, exclusive GST handling

- Added `gst_rates`, seeded with Singapore's 7%, 8%, and 9% historical periods and their Xero input
  and output tax codes.
- AR invoices freeze the applicable rate, effective date, and Xero tax type when they are created.
  A later GST-law change therefore does not rewrite an existing invoice.
- GST is calculated using exclusive line amounts. The Xero payload sends
  `LineAmountTypes: 'Exclusive'`, explicit tax types, and frozen line tax amounts.
- Future GST changes require a new effective-dated row in `gst_rates`; controller or frontend code
  should not be edited to hard-code a new percentage.

### 3. AP accounting controls

- Vendor invoices now capture due date, SGD currency, supplier GST registration number, GST
  treatment, date-effective GST snapshot, Xero expense account, subtotal excluding GST, GST, total
  including GST, rebate, and net payable.
- Supported GST treatments are standard-rated, zero-rated, exempt, non-GST, and disallowed input
  tax, each mapped to the appropriate Xero tax type.
- OCR requests the additional AP accounting fields and reconciles line items against the exclusive
  subtotal and printed GST breakdown.
- Line amounts are always derived server-side as quantity x unit price. Editing a line recalculates
  the invoice subtotal, GST, total, rebate, and net payable atomically.
- Approval is blocked when required accounting data is missing, dates are invalid, line arithmetic
  disagrees, GST is stale or inconsistent, totals do not reconcile, or a standard-rated supplier
  lacks a GST registration number.
- Low-confidence OCR requires the AP Specialist to explicitly confirm that the source PDF was
  checked before approval.
- Added an append-only `vendor_invoice_audits` table. Upload, extraction failure, header/line edits,
  approval, rejection, and Xero sync outcomes appear in the Invoice Review audit timeline.

### 4. Rebate, reporting, and Xero hardening

- AP Xero bills use exclusive accounting lines and a separate negative no-tax rebate line, so the
  Xero draft total equals EFAR's approved net payable without changing the supplier's printed GST.
- Vendor Expense Summary now tracks gross expenditure, rebate, and net payable independently. This
  fixes the previous double deduction of the rebate from `verified_total`.
- Both simulated and live Xero paths validate accounting totals before reporting success.
- Xero business-validation errors returned inside HTTP 200 responses are treated as failed syncs.
- AR Xero drafts now carry the EFAR invoice/booking reference and service date.
- The Xero settings screen clearly labels SIMULATION versus LIVE mode and explains token refresh
  behavior. OAuth state is single-use and expires instead of remaining valid indefinitely.

## Database and Setup

The two migrations were applied successfully to the configured development database during this
session. Both are idempotent and are included in `npm run db:setup` and `npm run db:reset`.

For an existing environment that has not received them:

```bash
cd backend
npm run db:migrate:gst
npm run db:migrate:ap-controls
```

The AP migration deliberately does not invent tax classifications for historical invoices. It
backfills unsynced legacy rows as non-GST and leaves AP to verify the source document.
